# ProGPU WPF Managed Subsystem Bring-up

## Porting Decision

For this port, "port" means reusing as much upstream managed WPF code as possible wherever it can compile and execute. ProGPU and Silk.NET are platform/rendering replacements at the boundary, not a reason to rewrite `System.Xaml`, `PresentationBuildTasks`, `PresentationCore`, `PresentationFramework`, controls, themes, resources, or the XAML compiler in the ProGPU bridge. New porting slices should first preserve the real managed subsystem path, then add the smallest native adapter or ProGPU primitive needed at the platform/render boundary.

The current architecture keeps this boundary:

- `System.Xaml` remains the real WPF XAML reader, schema, object writer, and markup-extension implementation.
- `PresentationBuildTasks` remains the real WPF XAML/BAML compiler path (`MarkupCompilePass1`, `MarkupCompilePass2`, `MarkupCompiler`, BAML writer/records).
- `PresentationFramework` remains the real WPF application, window, resource, style/template, control, document, and BAML/XAML loader implementation.
- `PresentationUI` remains the real WPF document/application support assembly. Windows builds keep the native `System.Printing` C++/CLI implementation, while non-Windows bring-up uses the existing `System.Printing-ref` project so the managed theme/XAML graph can compile without Visual C++ targets.
- Theme assemblies remain real WPF theme projects with `Page` XAML and internal markup compilation.
- `ProGPU.Wpf` supplies adapter services for rendering, retained scene ownership, portable windowing, input, dispatcher wakeups, and platform services without adding ProGPU references to the managed WPF subsystem projects.

## Basic App Smoke Ladder

1. **Managed core build gate**
   - Build `WindowsBase`, `System.Xaml`, `PresentationCore`, `PresentationFramework`, `PresentationUI`, `PresentationBuildTasks`, and at least one theme assembly.
   - Purpose: prove the upstream managed subsystem graph remains reusable on non-Windows.

2. **Code-only app gate**
   - Instantiate `Application`, `Window`, layout controls, text controls, resource dictionaries, and drawing visuals without XAML.
   - Route `Window.Show` through `PortableWindowActivationService` into the ProGPU/Silk.NET host.

3. **XAML compiler gate**
   - Build a tiny app with `ApplicationDefinition` and `Page` items using the real `PresentationBuildTasks`.
   - Verify generated BAML and code-behind connector paths are produced by WPF's compiler, not a ProGPU-local compiler.

4. **XAML runtime gate**
   - Load the generated app resources through real `PresentationFramework` BAML/XAML loaders.
   - Verify `ResourceDictionary`, `Style`, `ControlTemplate`, `VisualStateManager`, `StaticResource`, `x:Shared`, `DynamicResource`, and namescope behavior.

5. **Application run gate**
   - Call real `Application.Run()` on the compiled XAML app.
   - Verify WPF's own `StartupUri`, startup dispatcher work, root `Window.Show`, portable activation, run-loop handoff, shutdown, close, and dispose ordering without replacing managed app lifetime code.

6. **Theme gate**
   - Compile and load the Fluent theme project and representative style dictionaries (`Button`, `Window`, `RichTextBox`).
   - Verify themed controls render through the ProGPU retained scene bridge.

7. **Rich framework gate**
   - Exercise controls, routed input/commands, input bindings, focus, selection, `TextBox`, `RichTextBox`, `FlowDocument`, bindings, resources, and templates.
   - Keep failures attached to the real WPF subsystem that produced them instead of replacing the subsystem.

8. **Rendering integration gate**
   - Continue lowering WPF drawing, effects, brushes, text, 3D, retained invalidation, and dirty-branch replay to native ProGPU primitives.
   - Managed WPF should own semantics; ProGPU should own GPU execution.

## Portability Decisions Opened By The Harness

- Registry reads, ETW, Win32 system metrics/colors, keyboard-layout queries, cursors, font directories, DPI discovery, high-contrast/theme metadata, and hidden theme-notification HWNDs are now guarded with conservative non-Windows defaults only where the real framework smoke proved they were needed.
- UI Automation identifier initialization and composite-font parsing now have non-Windows guards for the shared OS-version helper and reserved-value probes. Basic selector/list controls and themed font metadata can initialize without loading `PresentationNative` or `UIAutomationCore`, while full provider/client integration remains a later platform-services item.
- Font-cache file mapping, Unicode classification table lookup, private-use icon-glyph classification/null-glyph placeholder layout, LineServices escape-string bootstrap, and the basic nominal-glyph `SimpleTextLine` quality gate now keep the Windows native paths on Windows and use managed non-Windows fallbacks for the real theme smoke. These are bring-up fallbacks for basic controls, layout, and visual replay; they are not a complete shaping, bidi, line-breaking, exact icon fallback, or paragraph-layout implementation.
- The non-Windows dispatcher path no longer creates the Win32 message-only HWND and now drains queued managed dispatcher work for `Application.Run()` startup/shutdown markers without calling Win32 `GetMessageW` or `MsgWaitForMultipleObjectsEx`. This is a bring-up gate, not the final loop. The final implementation should replace polling/drain behavior with the existing Silk.NET/ProGPU native-loop wake and dispatcher drain services.
- The real XAML runtime harness can now focus the shown XAML-created `TextBox` through WPF's own `Keyboard.Focus(...)` over `PortablePresentationSource`. The fix reuses WPF's window style/template, layout, inherited visibility, namescope, control, and focus logic; the portable branch supplies only the missing non-HWND root activation, root measure/arrange, and presentation-source boundary.
- The compiled storyboard slice verifies WPF's real BAML-created animation object model (`EventTrigger`, `BeginStoryboard`, `Storyboard`, and `DoubleAnimation`), real `Loaded` routed-event dispatch through WPF's own pending-loaded dispatcher path after portable show, the first zero-duration animated dependency-property value application through the disconnected non-Windows `MediaContext`/`TimeManager` path, and a non-Loaded `Button.Click` `EventTrigger` that starts a storyboard clock after an explicit render-priority drain. Broader animation timing, pause/seek/control actions, continuous clocks, and dirty-region policy remain open.
- The compiled template slice now verifies WPF's real `VisualStateManager` BAML path: `ControlTemplate` visual-state groups, `VisualState` storyboard metadata, and post-show `GoToElementState(...)` pressed-state application after a render-priority drain. Template-state semantics stay in WPF; ProGPU should only render the resulting visual state.
- The compiled input-binding slice verifies WPF's real `Window.InputBindings` BAML path: `KeyBinding`, `KeyGesture`, command parameter storage, and routed command execution through the existing `CommandBinding`. The latest extension raises `Ctrl+F6` through both the `ProGpuWpfWindowHost` platform-input callback and PresentationFramework's real `Window.HandlePortableInput(...)`, proving Silk.NET-normalized keyboard events can flow into WPF `InputManager`, `KeyBinding`, and `CommandManager` without a ProGPU command shortcut. IME/stylus and remaining key-routing edge cases stay in the same portable input boundary.
- Portable text input now reaches WPF's real `TextCompositionManager` and `TextBox` editor. The runtime and `Application.Run` harnesses focus the compiled `InputBox`, raise normalized text input through the ProGPU host and through PresentationFramework's portable input args, and verify WPF inserts the character, advances the caret, and clears selection. `SystemParameters.MouseVanish` now follows the same non-Windows fallback pattern as the earlier keyboard/caret metrics so `TextEditorTyping.HideCursor(...)` does not load `user32.dll`.
- Portable mouse input now reaches WPF's real `MouseDevice`, `InputManager`, capture manager, `ButtonBase` route, and `MouseWheel` routed event route. The runtime and `Application.Run` harnesses target the compiled `EventButton`, raise normalized move/down/up and wheel input through the ProGPU host and through PresentationFramework's portable input args, and verify the generated XAML `GotMouseCapture`, `LostMouseCapture`, `Click`, and `MouseWheel` handlers see WPF capture, `ButtonBase.Click`, and a one-line wheel delta of 120. The supporting source changes keep stylus/touch registry probing Windows-only, add a non-HWND global hit-test fallback for portable sources, and keep the new `RectangleGeometry` fill hit-test fallback narrow until ProGPU native vector hit testing replaces the remaining `MilCoreApi` helper dependency.
- The compiled section-control slice verifies WPF's real `TabControl`/`TabItem` BAML path: tab item headers/content, selected index/item/content state, generated selected content after portable show/run, and a selected-index change through WPF's selector/content-presenter machinery. The TabControl template also opened a line/polygon bounds dependency during hit-test precompute; non-Windows now uses a conservative managed `Geometry.GetBoundsHelper(...)` polygon-bounds fallback before `MilUtility_PolygonBounds`, with exact WPF-compatible vector bounds still assigned to ProGPU/native vector work.
- The section-control slice now also verifies WPF's real `Expander` and `GroupBox` `HeaderedContentControl` paths from BAML. The compiled app binds headers to the existing `SmokeDetail`, applies compiled `HeaderTemplate` resources, binds section content, and the runtime plus `Application.Run` harnesses validate generated header/content visuals and `Expander.IsExpanded` state changes without adding ProGPU-side control behavior.
- The compiled validation-manager slice now verifies WPF's real `BindingGroup` BAML path. The compiled app declares `StackPanel.BindingGroup` with a group-level custom `ValidationRule` and two explicit-update `TextBox` bindings; both real-WPF harnesses validate rule metadata, binding paths, rejected commits that preserve source values and set `Validation.HasError`, and accepted commits that update both source properties through WPF's binding engine. This keeps validation aggregation in WPF instead of adding a ProGPU-side validation shim.
- The compiled menu slice now verifies WPF's real `Menu`/`MenuItem` BAML path. The compiled app declares menu item hierarchy, separator, generated click handler, and command item metadata; both real-WPF harnesses validate the object graph, raise WPF's `MenuItem.ClickEvent`, and execute the compiled routed command from the compiled command target. The menu default template opened `SystemParameters.MenuPopupAnimation`; `SystemParameters.MenuAnimation` now follows the same non-Windows fallback pattern as the earlier text/input metrics before `SPI_GETMENUANIMATION`.
- The non-Windows theme-default path uses WPF's existing `Aero2` theme state for portable windows, while explicit theme harnesses can still load Fluent dictionaries through real `ResourceDictionary.Source`. `SystemResources` keeps the Windows `XamlAccessLevel.AssemblyAccessTo(...)` path on Windows and skips that unsupported platform call outside Windows.
- Scrollbar, caret, caret-blink, and primary-screen metrics, geometry bounds, bidi language checks, and TSF/text-services loading now have narrow non-Windows bring-up fallbacks opened by the real layout/focus/binding paths. Durable replacements should be Silk.NET/ProGPU platform metrics, ProGPU vector bounds, and cross-platform text services, not replacement XAML/framework code.
- `CompositionEngineLock` skips `wpfgfx_cor3.dll` on non-Windows so managed `MediaContext` startup can run disconnected while ProGPU owns render-data execution. Windows still uses the original MILCore lock and startup path.
- The default non-Windows DPI path is 96 DPI until a platform metrics service supplies real monitor/window DPI through the Silk.NET host.
