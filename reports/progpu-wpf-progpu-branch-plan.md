# ProGPU Branch Plan for WPF Port Acceleration

## Reuse Policy

The ProGPU branch should add reusable native primitives and shim behavior only where they let the WPF port keep real managed WPF code on the active path. Rendering, text rasterization, shader effects, vector geometry, image upload, cache/lifetime, and backend resource fixes belong in ProGPU when the alternative would be a WPF-bridge workaround or managed-side pixel/vector emulation. XAML, controls, resources, styles/templates, routed events/commands, layout metadata, application lifetime, and theme dictionaries should stay in the WPF superproject and continue to use upstream managed WPF code.

## Decisions

- Keep feature work that accelerates WPF rendering fidelity in the ProGPU branch when it improves the backend model directly, instead of compensating in the WPF bridge.
- Keep WPF arc semantics in ProGPU vector primitives. The WPF bridge may adapt WPF types, but affine arc math, sweep flipping, and shader-rasterized arc records belong in `ProGPU.Vector`/`ProGPU.Scene`.
- Preserve API-level rounded-rectangle radii before they reach the bridge. WPF `radiusX`/`radiusY` and Skia per-corner radii should remain native ProGPU command/path data, with only uniform scalar cases using the compositor's fast rounded-rect primitive path.
- Preserve host-level per-corner corner radii as geometry when the host platform API cannot express them as independent radii. Do not collapse asymmetric `CornerRadius` values to a uniform max-radius clip in host controls, because that clips square corners that WPF/Avalonia semantics leave uncut.
- Keep WPF/WinUI path API shims from erasing arcs before rendering. Parsed `ArcSegment` values should stay native ProGPU arcs, and WPF `Geometry.Transform` should be passed as command transform metadata so ProGPU owns affine arc evaluation. Degenerate arcs may fall back only inside the ProGPU vector layer where shader parameters cannot be produced.
- Prefer fixed-quad shader primitives for WPF-compatible arc strokes. CPU flattening should be limited to degenerate arcs that cannot produce valid shader parameters; parametric strip tessellation should not be reintroduced as a WPF bridge workaround.
- Preserve WPF clip geometry as ProGPU geometry masks whenever the source geometry can be represented as a ProGPU vector path. Rectangular fallback is acceptable only for unsupported geometry forms, and rotated/sheared fallback bounds must still include all transformed corners.
- Keep WPF geometry API shims non-mutating and query-correct. Geometry bounds must apply the current transform through ProGPU vector helpers before rendering, not by copying state during `Draw()`, because WPF layout, hit-testing, clipping, and retained cache sizing commonly query bounds before render replay.
- Treat subtractive and inverse clip/fill semantics as native path-op work. Skia `Difference` clips, inverse fills, and WPF `CombinedGeometry.Exclude` should feed ProGPU combined geometry and the WebGPU path-op/mask pipeline rather than managed bridge-side region emulation.
- Treat GDI/WPF text-size unit conversion as a shim/backend responsibility before native text layout. The WPF bridge should pass source font intent through; ProGPU should normalize point/document/inch/millimeter sizes against the active graphics DPI rather than asking bridge code to pre-scale text.
- Preserve text run boundaries in ProGPU shims. Mixed fonts, fallback runs, and positioned glyph spans should remain explicit `SKTextBlob`/glyph-run data that the backend can draw natively instead of being collapsed or re-split in the WPF bridge.
- Treat color-layer glyph interleaving as compositor batch ownership. COLR/CPAL vector layer output may switch to path rendering, but text buffers should expose only committed glyph instances and resume text batching afterward rather than asking WPF bridge code to split glyph runs.
- Treat texture alpha convention as backend texture metadata, not as a pipeline-name heuristic or WPF bridge concern. Upload paths that know they contain straight RGBA should mark that explicitly; render targets and PBgra uploads should remain premultiplied so layer/effect composition stays stable.
- Treat fixed-function advanced blend limitations as backend shader/pipeline specialization work. When WebGPU blend factors require premultiplied source RGB for WPF-compatible `Screen`, `Multiply`, or `DstOver`, ProGPU should choose native fragment variants or effect wrappers that produce the right source convention rather than asking WPF bridge code to rewrite colors or shaders.
- Treat WebGPU shader resource capacity limits as backend draw-time limits, not WPF managed-effect state. A WPF shader effect that uses every logical sampler register can skip a masked draw on devices that cannot also bind the mask texture/sampler, but that limitation must not poison cached/reused effect parameters once the mask scope is gone.
- Treat mutable effect invalidation as native scene ownership. Effects may be shared across visuals, so ProGPU effect descriptors should invalidate weakly tracked visual owners and let parent dirty propagation refresh cached layers instead of relying on WPF bridge polling or managed replay invalidation workarounds.
- Treat backend render-target ownership as explicit. A shim surface may borrow a ProGPU `GpuTexture` and render into it directly; backend handles from APIs this WebGPU context cannot mutate must fail rather than allocating a hidden replacement texture.
- Preserve backend texture metadata through shim snapshots. Surface snapshots should retain the source texture format and alpha convention instead of coercing into RGBA and expecting downstream WPF/Skia bridge code to repair channel interpretation.
- Preserve surface contents inside backend shims across incremental flushes. Skia/GDI-style surfaces should track whether a render target already has valid contents and request native load operations where the source API expects persistent pixels, rather than forcing WPF bridge code to replay previous draw batches.
- Treat SKPaint blend modes, save-layer paint application, and encoded-image alpha conversion as Skia shim/backend responsibilities. The WPF bridge should issue WPF/Skia drawing intent and let ProGPU map supported blend modes and alpha conventions into native command state and texture metadata.
- Treat Skia save-layer image filters as native layer operations. `SaveLayer` should route supported `SKPaint.ImageFilter` values through ProGPU image/effect pipelines and fail closed for future unsupported filters instead of silently compositing the unfiltered layer or asking WPF bridge code to emulate pixels.
- Treat Skia surface flush cleanup as shim/backend ownership. `SKSurface.Flush()` must release command-retained image resources and `SaveLayer` textures on both success and failure paths, because WPF/Skia callers should not need managed-side retry or disposal workarounds to avoid native texture leaks after a failed render/readback.
- Treat zero-copy shared-image lifetime as host/backend ownership. `ProGpuHostControl` must revalidate captured resources after async map/update awaits and abandon stale frames when detach, cleanup, or fallback replaces the current zero-copy state, because WPF and Avalonia callers should not need to guard shared WebGPU resources around host lifetime races.
- Treat Skia/WPF dash, gradient spread, and image-effect color-space semantics as backend responsibilities. Dash spans, tile/spread mode mapping, and straight/premultiplied image-effect color math should stay in ProGPU vector/shader code rather than in WPF bridge adapters.
- Treat GDI world-transform stroke thickness as shim/backend state. WPF and GDI callers should pass source geometry and pen intent through; ProGPU should convert that into native command thickness or transformed command state rather than bridge-side outline inflation.
- Treat Skia canvas transforms and WPF pushed transforms as shim/backend stroke state. When the backend consumes scalar pen thickness in device space, ProGPU shims should derive that thickness from the active transform and leave WPF managed rendering managers focused on source pen/geometry intent.
- Treat unsupported Skia gradient and backend-origin cases as backend capability gaps. Two-point conical gradients and bottom-left ProGPU backend render targets now have native support; future unsupported cases should either fail closed or gain native shader/render-target support in ProGPU, not bridge-side CPU compensation.
- Treat effect coordinate systems and extension frame cleanup as compositor responsibilities. HiDPI mask uniforms, logical versus physical effect quads, BGRA readback swizzling, skipped layer cleanup, and offscreen-only extension resource pruning should be fixed in ProGPU native render/effect/shim code rather than compensated in WPF managed replay.
- Keep WPF-specific type adaptation in `src/ProGPU.Wpf` until the real WPF `PresentationCore` and ProGPU shim type identities are unified.
- Prefer adding reusable ProGPU primitives for WPF concepts that also benefit other frontends: exact path stroking, gradient tables, texture sampling modes, text flags, mesh extensions, image effects, and retained resource lifetime helpers.
- Treat render-thread WebGPU context availability as a backend/compositor invariant. Host integrations should not compensate for thread-static context state; compositor render entry points should publish their active context while backend resources should remember their owning context for cleanup and cache reuse.
- Use signed ProGPU assemblies for direct references from strong-named WPF assemblies when the TFM/project graph is compatible. Until then, source-share small ProGPU-owned helpers only when they remain internal to WPF and avoid exposing ProGPU namespaces as WPF public API.
- Treat XAML loading, writing, resource-key conversion, resource dictionaries, and theme object graphs as WPF-owned managed behavior. When a serializer gap appears, first repair the reused WPF serializer path, as with `SystemResourceKey`/`SystemThemeKey` emission through `SystemKeyConverter`; only move work to ProGPU when the missing piece is a native rendering, shader, vector, text, image, or platform capability.
- Treat visual opacity-mask execution as native ProGPU retained scene work. `Visual.OpacityMask` and `Visual.OpacityMaskBounds` now let the WPF bridge set supported bounded masks as native retained visual state, so masked WPF descendants can remain separate retained child visuals without bridge-side inline replay or managed mask emulation.

- Composition: build on retained `ChangeVersion` counters, native `CacheAsLayer` lowering for WPF visual and drawing-group `CacheMode`, retained `Visual.OpacityMask`/`OpacityMaskBounds` lowering for bounded WPF visual opacity masks, effect render cache keys, reflected WPF source version polling with dirty-source identity, dispatcher/timer render scheduling, the first MediaContext render-priority wakeup/dispatcher-flush bridge, disconnected managed animation ticks, the first host-level frame-state gate, clean-source retained WPF replay skips, and `WpfRetainedVisualBranchMap` dirtying mapped native branches for reflected WPF source objects while falling back when any dirty source is still unmapped or shares a native branch with clean source owners. Preserved-retained-root frames keep provider-created owner contexts on the flat fallback to avoid appending stale branches outside a skipped or partial replay target. Continue toward dirty-region policy, partial retained-branch replay, resource-to-visual ownership mapping beyond reflected source visual branches, unbounded/advanced mask resource handling, and full MediaContext integration so WPF `Freezable`/visual/effect/cache invalidation can skip unchanged retained branches without replaying the full reflected tree. - Windowing: keep Silk.NET surface and input abstractions in ProGPU reusable enough for WPF's eventual `CompositionTarget` replacement, including resize, title/client-size updates, DPI, activation, file-drop, cursor, timer, dispatcher scheduling, and render wakeup hooks.
